# whatsBird 验收与优化建议

2026-09-14，验收对象为当前工作目录源码及随包 v2 分类模型。结论：相机、识别链路和照片保存已形成可运行的技术原型，但尚不能按“可靠实时识别中国大陆常见鸟类”通过功能质量验收。主要差距是识别质量、评测资料的独立性和漏检后的分类恢复；同时存在性能统计失真及故障降级不完整的问题。本轮未修改业务代码、模型、数据集或用户设置，只增加本报告与验收证据。

本次重新构建当前源码并覆盖安装到在线的 Redmi Note 8 Pro（Android 10），保留应用数据；原已安装 APK 的模型与当前模型一致，但应用代码不完全相同，因此没有直接沿用旧包的运行结果。设备测试 APK 与当前构建产物 SHA-256 一致。随包分类模型与 `ml/out2/classifier_float16.tflite` 完全一致，SHA-256 为 `1a207e39023f686a1e76f1129800fe73972b5d4b4925267d5b88d534e193060f`；检测模型 SHA-256 为 `5d4ebec1029bc9907aeadb9e7b4ac9cb1da6a19d01ad375210a9ae18ba173302`。源码的新安装默认门限是 0.55，而测试手机保留的用户设置是 0.60，两者须明确区分。

**P1：目前用于选门限和比较模型的跨版本测试集含旧训练资料。** 当前 `AppSettings.kt` 用 v2 模型在 `data2` 的 1,612 张测试图上取得的成绩解释默认 0.55；逐条核对两个 manifest 后，其中 570 个源照片 ID 已在 `data` 的训练集中出现，按观察事件统计涉及 578 条测试记录。例如 photo_id=57905803 的旧训练图为 240×180，新测试图为 500×375，分辨率变化没有形成独立测试样本。`out4/train_metrics.json` 还表明 out4 从 `out2/best.keras` 继续训练，因此清理 data2 当前目录并不能消除继承权重已见过的资料。建议跨所有数据版本及初始化模型追溯训练来源，固定观察事件的 split，新增测试集时排除全部训练祖先见过的照片；门限在验证集选择，最终成绩在另外保留的测试集上报告。相关位置：[默认门限依据](../android/app/src/main/java/com/whatsbird/settings/AppSettings.kt#L40)、[切分逻辑](../ml/fetch_inat.py#L223)、out4 训练记录（本地资料 `ml/out4/train_metrics.json`，未公开）。

本轮以当前随包模型重跑 `ml/data` 现有的 823 条测试记录，它们与该数据集训练部分没有源照片或观察事件重叠。删除同图异标签的 2 条记录后，剩余 821 张，其中目标鸟 757 张、清单外鸟 34 张、非鸟 30 张；在新安装默认门限 0.55、候选差距至少 0.15 下，318/757 张目标鸟获得种名，即覆盖率 42.0%，其中 244/318 正确，即已命名正确率 76.7%，清单外鸟误报为 8/34，即 23.5%，非鸟误报为 4/30。它们明显低于原方案讨论的正确率 90%、覆盖率 70%、清单外误报不超过 10%。这些是整图中心裁剪的单次分类结果，既没有走检测框裁剪，也没有走实时多帧稳定或静态镜像平均，不能直接表述成野外实时准确率；该旧测试集还被历史阈值分析使用过，最终验收仍需新增未参与调参的样本。建议首先修复同图异标签资料，当前 data 中仍有 87 张源照片被赋予多个类别，data2 中有 170 张，而现有完整性脚本会报告 OK；随后补充鸟框裁剪、易混淆种及清单外鸟的样本，并分别评测实时与静态照片的实际推理路径。仅降低门限不能解决目前的精度差距。

**P1：鸟短暂漏检后可能永久失去分类任务。** `BirdPipeline.drainQueue()` 发现任务对应目标的 `missedFrames>0` 时，回收裁剪图后直接 `continue`，没有将仍然存活的 `TrackMemory.enqueued` 清回 false；同一跟踪 ID 再次被检测到后，`handleDetections()` 会持续因这个标志跳过分类。追加探针实际构造“已入队 → 暂时漏检 → 队列丢弃 → 同 ID 重现”，复现了标志仍为 true 的失败。建议在所有任务退出路径统一释放在途标志和位图，并给任务附加跟踪代次、结果过期检查，覆盖短暂遮挡、拍照占用分类器、旋转或重建管道后的恢复。相关位置：[任务丢弃分支](../android/app/src/main/java/com/whatsbird/pipeline/BirdPipeline.kt#L273)、[跳过已入队目标](../android/app/src/main/java/com/whatsbird/pipeline/BirdPipeline.kt#L235)。

**P2：检测帧率统计不能用于当前性能验收。** `updateStats()` 在成功检测、节流丢帧和拒收帧时都会增加 `frameCounter`，随后将它作为 detectionFps；classificationFps 则是平均单次耗时的倒数，不是实际完成任务数。追加探针在没有任何检测完成的情况下触发 20 次统计更新，得到 20 FPS，预期应为 0；真机日志也出现了目标频率为 8、单次检测约 214 ms，却上报约 19 FPS 的情况。建议分别计数收到的帧、实际完成的检测、实际完成的分类以及丢帧，预览 FPS 单独测量；再测首次稳定种名延迟 P50/P95、同屏多鸟时的更新间隔和持续发热后的降速。相关位置：[计数实现](../android/app/src/main/java/com/whatsbird/pipeline/BirdPipeline.kt#L350)。

**P2：模型故障恢复和普通拍照仍被耦合。** 源码中的异步检测错误回调只通知错误，没有清除 `inflightBitmap` 与回调槽位，而后续帧遇到非空槽位就直接拒收；这一错误分支存在停扫后不自动恢复的路径，尚未在真机注入底层错误。检测模型构造失败时 `ScanViewModel` 又会把 `capture` 设置成 null，`refreshCaptureHandler()` 也要求 detector 非空，因此原方案要求的“模型不可用时仍允许普通拍照”没有实现。建议让相机与原图保存独立工作，检测器错误时清理在途状态并执行有界重建；标签处理失败应明确反馈，但不要关闭基本快门能力。相关位置：[检测错误回调](../android/app/src/main/java/com/whatsbird/detect/BirdDetector.kt#L68)、[拒收条件](../android/app/src/main/java/com/whatsbird/detect/BirdDetector.kt#L95)、[拍照处理器条件](../android/app/src/main/java/com/whatsbird/ui/ScanViewModel.kt#L241)。

**P2：保存异常仍可能被包装成成功。** `MediaStoreSaver.finish()` 用 `runCatching` 吞掉解除 `IS_PENDING` 时的错误，也没有检查 update 的影响行数，上层随后直接返回 Saved；发生该异常时，文件可能仍未公开给系统相册，界面却提示成功。静态检测器的异常又被转换为空检测列表，拍照处理器据此生成无标注副本，无法区分“确实没有鸟”和“模型处理失败”。本轮正常保存已通过，这两项属于源码确认的异常路径，尚未在真机注入存储或模型故障。建议把写入、媒体发布、识别结果与标签副本完成状态分别返回，只有确实无目标时才显示无目标；模型失败时保存原图并显示标签未完成。相关位置：[媒体发布](../android/app/src/main/java/com/whatsbird/capture/MediaStoreSaver.kt#L94)、[静态检测错误处理](../android/app/src/main/java/com/whatsbird/detect/BirdDetector.kt#L113)。

**P2：设置页说明与实测结果冲突，工程检查也缺少阻断。** 页面声称“清单外的鸟一律显示鸟类，不会猜”，但本轮离线和真机样本都出现了清单外误命名；55% 门限对应“约六分之五正确”的说明又来自含旧训练图的测试集，应先撤下这种确定性表述。面向用户建议提供“更保守／平衡／更多候选”等有实际验证依据的选择，将原始模型门限、GPU 开关和模型版本移入高级设置，并提供可查看的支持鸟种清单。Lint 当前唯一 Error 为 `CameraScreen.kt:88` 的 `NonObservableLocale`，而 `abortOnError=false` 将它隐藏在成功任务中，应修复实际错误并恢复错误阻断；35 个 Warning 中包含大量依赖升级提示，不建议为了验收一次性升级所有依赖。相关位置：[设置说明](../android/app/src/main/res/values/strings.xml#L47)、[Lint 错误](../android/app/src/main/java/com/whatsbird/ui/CameraScreen.kt#L88)、[Lint 配置](../android/app/build.gradle.kts#L73)。

实时标签目前锚定在鸟的检测框上方，具备避让逻辑，但没有头部关键点模型，也没有独立于检测结果的连续位置插值。相机预览、基础界面、设置页及相册跳转本轮已查看，当前画面没有真实鸟，因此不能把注入一张静态白头鹎照片的成功推广为多鸟移动验收。后续应录制或采集有鸟种及目标身份标注的 1、3、5 鸟视频，覆盖交叉、遮挡、出入画面、变焦、旋转和拍照瞬间移动；分别记录漏检、错名、身份交换、标签滞留和首个稳定种名延迟，并完成至少 15 分钟持续扫描及另一台手机的检查。

建议执行顺序为：先修复漏检后的分类恢复和性能统计，再冻结跨版本独立的数据划分、清理同图异标签并重做默认门限评估，然后补齐模型故障时的拍照与保存状态，最后优化标签跟随和设置页。下一次验收的必要证据是当前 APK 对应模型与资料版本、无训练重叠的测试报告、真实多鸟视频的端到端结果，以及持续运行数据。无需先扩展更多鸟种或增加页面，先让已经宣称支持的鸟种达到可用质量。

复现资料保存在 [本轮证据目录](acceptance/2026-09-14)。原有测试命令为 `./gradlew :app:testDebugUnitTest :app:lintDebug :app:assembleDebug :app:assembleDebugAndroidTest`，工作目录是 `android`。两项缺陷探针保存在证据目录的 `probes` 内，从项目根目录执行 `./android/gradlew -p android -I docs/acceptance/2026-09-14/probes/audit.init.gradle :app:testDebugUnitTest --tests com.whatsbird.audit.AuditRegressionTest` 可再次复现；它们目前预期失败，未加入应用的常规测试源目录。探针运行后已恢复并重跑原有 25 项测试，全部通过。
